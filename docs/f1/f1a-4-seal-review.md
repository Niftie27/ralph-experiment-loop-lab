## Q1. Research parse: complete routing/error audit

**reasoning — convention:** The following describes the default seal, source bounds from `fundingSource`, and synthetic inputs only. Every `fail` adds `Vision funding: `; `<file>` below is the public source filename. October 2025 is sealable but not wholly sealed.

- **reasoning — lines 61-66:** Empty bytes or missing final LF throw `<file>: file does not end with a newline`, before any routing. Header mismatch throws `<file>: unknown header (expected the exact Vision header or a numeric first row)`. Thus a missing LF on the sealed suffix changes success into failure without exposing a row number. A headerless first line not beginning with a digit takes the header error even if someone intended it as a malformed sealed timestamp; its intended time is unknowable. No claim that malformed text represents an actual before/at/after-seal time is valid.
- **reasoning — lines 67-77:** Only the substring before the first comma (or the whole line if there is no comma) is interpreted as `calc_time`. A short/non-13-digit/malformed time in October throws `calc_time unreadable in the research or sealed part` if no sealed time has yet been recognized, or `calc_time unreadable in the sealed part` after one. Both lack row numbers. In a wholly sealed source the latter applies immediately. In an ordinary wholly research source it is `row N: calc_time is not 13 digits`. `N` is physical line number `n+1`, including the header when present.
- **reasoning — lines 79-81:** Valid 13-digit times outside the source month throw `calc_time outside the file month in the sealed part` if the current time or previous time is sealed; otherwise `row N: calc_time outside the file month`. In October a September time before a sealed row therefore has a numbered research error; after a sealed row it has a sanitized-location error. A November time in October always has the sealed error. The seal itself is inside October, not an out-of-month time. In a different month's file, an at-seal timestamp is outside-month but still uses the sealed error.
- **reasoning — lines 83-88:** A nonincreasing time throws `calc_time order broken in the sealed part` when `previous` is sealed, otherwise `row N: calc_time not after the previous row`. Every accepted timestamp, including a sealed timestamp, becomes `previous`; then sealed rows skip all field/rate/interval work. Consequently a research-time row following a sealed row cannot reach a numbered field diagnostic or enter columns: it fails the earlier bounds/order check. A duplicate sealed timestamp also fails, whereas two increasing sealed timestamps in one settlement hour are not checked for duplicate hour on this path.
- **reasoning — lines 89-97:** These are reachable only for a research timestamp after the routing checks. Messages are `row N: expected 3 fields, found K`, `row N: calc_time is not within 15,000 ms after the full hour`, `row N: two rows in one settlement hour`, `row N: interval not one of 1, 2, 4, 8`, or the canonical-rate reason (`malformed rate token`, `rate has more than 8 exact decimal places`, `rate is not a finite Number`). The rate token itself is not interpolated. A short row with a valid research timestamp fails field count; the same short row at/after the seal, even just the timestamp plus LF, skips those checks. Offset and interval poison on sealed rows likewise cannot affect columns.
- **reasoning — result/control flow:** Valid sealed rows contribute nothing to returned arrays, `rateDecimal` or `rowCount`; count is `calcTime.length`, not total lines. They can affect success/failure and the routing predecessor but never the research schedule predecessor. No enumerated default-path message names a sealed row number, timestamp, field value or count. F2 is the narrower failure-class disclosure. Entire-buffer decoding/splitting and loop length depend on protected bytes even though only their first field is semantically interpreted; allocation/time are not constant.

## Q6. Bytes identity

- **reasoning:** `loadSource` rejects more than one visible local version before reading. `readVerifiedSource` reads CHECKSUM text and one zip Buffer, verifies that Buffer's sha against the named checksum and version-directory sha, then returns that same Buffer. `readZipMember` parses that Buffer, not a second filesystem read. Replacing the file after verification therefore does not change the parsed in-memory bytes; changing it during the initial read either produces a Buffer matching the expected hash or fails verification, subject to ordinary SHA-256 assumptions.
- **reasoning:** Symlinks are followed; there is no no-follow policy or inode lock. A target with wrong bytes cannot pass the hash comparison simply because it is a symlink. A symlink to identical verified bytes is still the same byte identity. Replacing both checksum and zip while retaining a different directory sha also fails the directory-sha comparison. This is local integrity against the stored checksum, not independent proof that a maliciously replaced checksum came from the publisher.
- **reasoning:** Concurrent appearance of a second version after enumeration is not locked out, and research/holdout calls reload October separately. Thus one atomic store snapshot across a verify/read is not guaranteed; each returned Buffer is individually bound. A concurrent republish can violate the single-version policy or make the two paths see different source versions without any individual unverified Buffer being parsed. This is a concurrency limitation, not a demonstrated checksum/read TOCTOU substitution.
- **reasoning:** The zip helper requires exactly one central-directory member, expected name, supported deflate/flags, matching local-name metadata, bounded inflated size and CRC. A declared extra or wrong member fails; malformed names/sizes can appear in research errors for the mixed file, while the integrity try hides them. Its single-member rule is about the declared central directory; a claim that every unused/padding byte or hidden local header is forbidden is not established. All such bytes still participate in the zip sha.
