## Q2. C16, C17, C18 implementation

**reasoning — C16:** P0 exactly states zero tolerance after one completion pass and the April–September verified-empty condition; F2 defines that completion pass and retains the frozen sample. No objection to those decisions. However V3 (P2) gives a missing CHECKSUM two different statuses under I1 and F2, which also changes whether it is eligible for completion. The outcome remains inconclusive if either status persists, but the acquisition procedure and reported reason differ.

**reasoning — C17:** P3 implements the v2 review's alternative coverage floor: an hourly-related eligible pair in each later era and at least one observed outer boundary. In v3, hourly-related already means eligible. An observed entry has its first run row inside W; an observed exit follows a retained run's last row inside W, so its existing successor is also inside W. Consequently omitting the repeated adjective eligible from observed boundary does not widen the predicate. P3's all-outcome claim restriction and P2's observed-direction/regime restriction implement C17 without a new literal conflict. Determining the documented regime inventory remains U8, not a reason to re-argue the floor.

**reasoning — C18:** P5 implements Claude's role-none decision, P1 limits compatibility to hourly-related pairs, and P2 preserves every role-none class. P5 also requires the count and unexplained qualification in both P1 and P2 statements; P2 need not repeat that cross-cutting requirement. Role-none stops cannot choose P1 versus P2, though other P0 conditions can independently apply to the same source. No contradiction identified and no alternative policy proposed.

## Q4. F07 absolute-sentence audit

**reasoning — V1, P1, literal conflict: O7 versus I1/I2 sealed-row prohibition.** O7 selects raw bytes by key month, not by the timestamps actually inside them. Consider an otherwise valid April-key archive containing an additional well-formed routing token at the seal. I2 drops that row before checking its month, so the source can be verified_nonempty; O7 then exports its raw bytes. I1 authorizes no export of sealed rows. Excluding October keys does not resolve this counterexample, even without any corrupt archive or parsing failure. This is a logical permitted-input example, not an assertion that such a file exists. The unresolved choice is how raw-fixture eligibility enforces the existing seal boundary; no alternative fixture policy is selected here.

**reasoning — V2, P2, literal conflict: I1 versus O7 excluded fixtures.** I1 says “No row of an excluded or not-verified file enters any output.” O7 selects the first eligible-month key for each exclusion check and exports fetched raw bytes. A fetched single-member CSV with a pre-seal interval failure is an excluded file with rows, but those rows are in its raw fixture output. The explicit exception in O covers rates, not I1's excluded-row prohibition. This conflict is separate from V1: it exists with only pre-seal rows and no rate disclosure beyond the accepted exception.

**reasoning — V3, P2, literal conflict: I1 versus F2 status/retry.** After a CHECKSUM is established absent by HTTP 404 through the permitted retry, I1 prescribes excluded:missing_checksum. F2 says a source object, explicitly including CHECKSUM, failing after one retry is not_verified. Only the latter is re-attempted in completion; I1/F3 forbid retrying excluded keys. F4 prioritizes F1–F3 over generic acquisition retries, but does not explicitly subordinate F2's status assignment to I1's absence rule. The same established absence therefore has two prescribed status paths. C16's zero tolerance does not remove that conflict.

**reasoning — V4, P3, literal conflict: O universal encoding versus O7 raw bytes.** “Every file: UTF-8, LF line ends” includes the exactly-as-fetched binary ZIP outputs of O7. Re-encoding those archives would violate their raw identity and source hashes. The rate exception does not state an encoding exception. This is a wording conflict, not an argument against raw fixtures.

## Q5. Implementability from stated inputs

**reasoning — scope:** V1–V4 need reconciliation as identified above. The following are missing choices or inputs, not proposals for new policy; none asserts an observed production defect. Items explicitly deferred to a future run document are identified as such rather than treated as contradictions.

- **reasoning — U1, P2, S1/I1, object exceptions and transport identity:** Other object names can mean everything except canonical ZIPs, or everything except ZIPs and the separately mentioned CHECKSUM sidecars. Only the second reading permits I1's required checksum fetch. The precise sidecar exception, listing prefix representation in O8 (symbol versus root-relative prefix with slash), and exact key-to-request encoding need one shared definition; implementations must not normalize an allowed external identifier into an excluded one.
- **reasoning — U2, P2, S3, overlapping availability predicates:** Verified August and September can have rows bracketing the whole window but none inside it; S3 expressly does not certify missing-settlement absence. That satisfies both the available predicate and the unavailable predicate. Unlike D2, S3 does not state first-match precedence. Missing choice: priority between those two statuses. This is counted as ambiguous decision ordering, not a second policy proposal or a proven event.
- **reasoning — U3, P2, I1/I2, rejection grammar and precedence:** The CHECKSUM text grammar is not fixed for multiple digest lines, malformed digest tokens, binary markers or trailing material; the filename equality alone is insufficient. Archive-structure acceptance and the check-name vocabulary are also not fully specified. I2 lists framing before the row checks but does not place it in their first-failure order: an unterminated pre-seal row can also have bad fields, and an earlier row can already fail. Missing choices: exact accepted checksum/archive forms and deterministic first-failure order/names, including framing versus earlier row failures. These affect fixtures and exclusion counts, not just implementation style.
- **reasoning — U4, P2, O7/E2, negative and incomplete fixtures:** For fetched excluded:hash, excluded:CRC or excluded:interval fixtures, E2 needs to distinguish reproduction of the expected source rejection from an implementation disagreement. Its explicit status-only exception handles no-byte fixtures, not those fetched negative cases. The required extraction projection must also mean retained pre-seal rows, not every extracted row. Missing choices: status-comparison protocol and when extraction is forbidden, plus treatment of partially received zip/sidecar bytes and a TREE key absent from the frozen list. This preserves the approved raw-fixture decision rather than replacing it.
- **reasoning — U5, P2, O5/O6/E1/E3/P1, canonical reporting:** CSV schemas and most row sorts are fixed, but O6 has no canonical text schema, order or zero-count convention for E1 tuples/status totals; distinct label pattern in P1 has no precise definition. Missing choices: summary/domain serialization, the enumerated documented zero-evidence patterns, and the label-pattern equivalence relation. E2's byte comparison of counts/outcome requires an agreed representation even if it does not compare the whole summary file.
- **reasoning — U6, P3, O7/O11, artifact naming/order:** Fixture output paths and the order/path spelling of O11 checksum lines are not specified; raw source sidecar names alone do not specify a repository output layout. Missing choices: one artifact map, checksum-line ordering and relative-path convention. Compression and delivery sizing are explicitly deferred to the run document and are not an independent conflict.
- **reasoning — U7, P2, E2/P0, independent outcome input:** O0/O4/O8 supply row and final-source-status decisions, but not the observed dependency identities/Node version, acquisition failures before a freeze exists, or the result of E2's fixture verification. Missing choice: how those external validity inputs are passed to the P recomputation and which result stage is compared. A run cannot derive its own parity failure solely from the same timing rows. Expected dependency hashes must be bound to a specified local import closure at the pin; the recorded hash list is not by itself its expected baseline.
- **reasoning — U8, P2, E3/P1/P2/P3, documented regimes:** Observed role/era cells are deterministically derivable; documented regime/direction, applicable document scope, documented discriminator, unique generic amendment and synthetic validation adequacy are not derivable solely from O0/O4/O8. The contract supplies narrative examples, not a complete machine-readable applicability inventory or candidate-rule enumeration. Missing inputs: the frozen documentation-to-case mapping and amendment/fixture definitions, or an explicit human-decision boundary for those judgments. No replacement applicability or outcome policy is proposed.
- **reasoning — U9, P2, F1/F5/F6, run-document parameters:** Finite pagination/transport timeouts, exact decompression/line/output-space bounds, monitored accounting, invalid-marker schema/location and publication boundary are not all fixed in v3. Most resource choices are expressly delegated to the run document; they are not evidence that the stated numerical ceilings conflict. A script cannot choose those bounds or canonical failure artifacts from this text alone. The missing input is that frozen tested run configuration, not permission to relax a ceiling.
- **reasoning — U10, P2, P2/P6, future protected protocol:** Sanitization is required, but input-version selection, exact approved command, dependency closure, output schema, global single-invocation accounting and synthetic results are future artifacts, not provided inputs. P6's narrow disclosure cannot be implemented merely by calling the existing ordinary CLI. This is an acknowledged later prerequisite, not a finding that v3 already authorizes such a call and not a request to consume it now.

## Q6. Leak paths

**reasoning — P1 V1, sealed rows:** The selected key's month does not prove the timestamp of every raw row. I2 deliberately omits month validation for sealed rows, so even a verified April–September fixture can export one. Excluded raw fixtures provide an additional route through unknown contents, not a separate counted finding. A CHECKSUM match authenticates bytes; it does not establish that those bytes meet the seal restriction. No actual source contents were inspected.

**reasoning — P2 V2/U4, excluded rows:** O7's negative-fixture selection can publish rows I1 forbids in outputs; E2 also lacks a precise rejected-fixture extraction boundary. Parsing every extracted field, rather than only the approved timing projection/status, would read rates beyond the permitted opaque raw-byte exception. Such rate parsing is forbidden by O/I2, not implicitly authorized by E2.

**reasoning — six-symbol paths:** S1 removes the six before listing below their prefixes and freezes only canonical external-symbol keys. Receiving six prefix names and reporting their removal is expressly allowed; it is not listing their files. No direct sanctioned path to their files was identified in those selection rules. Correct request/key encoding and import behavior still need the frozen implementation; their runtime enforcement is not verified. This is not counted as a contradiction or a claim of tested safety.

**reasoning — P2 U10, protected disclosure:** The later P6 boundary is necessary because an ordinary verify call can expose more than unit results, as taken over from v3 P6 and the prior review. The spec states the prerequisite and does not authorize bypassing it. A six-file read by that separately approved integrity path is not a gate read; leaking its rows, telemetry or exceptions would violate P6. No such invocation occurred here.

**reasoning — remaining permitted/forbidden distinctions:** O0–O6/O8–O10 use accepted pre-seal timing rows and metadata, not rate values; O7's raw rate bytes are the explicit accepted exception. October hashes are opaque provenance, not rows or byte-size statistics. I2's routing token and I1's opaque integrity processing are explicitly permitted sealed-byte operations; retained timing outputs do not intentionally include routed-out timestamps. No additional direct rate or six-file disclosure is established by the read text. Actual content hygiene and implementation delivery remain not verified.
